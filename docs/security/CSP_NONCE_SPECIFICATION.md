# CSP Nonce Specification

This specification defines WorkSphere's nonce-based Content Security Policy
(CSP), the request-to-browser propagation path, and the checks required to
evaluate a strict policy in Next.js.

## 1. Scope and source of truth

The canonical implementation is:

- [`src/lib/security/csp.ts`](../../src/lib/security/csp.ts): nonce and CSP
  construction.
- [`src/lib/middleware/handlers/securityHeadersHandler.ts`](../../src/lib/middleware/handlers/securityHeadersHandler.ts):
  request and response header propagation.
- [`src/lib/middleware/chain.ts`](../../src/lib/middleware/chain.ts): the
  composed middleware pipeline.
- [`src/app/layout.tsx`](../../src/app/layout.tsx): server-side nonce
  consumption for the theme bootstrap script.

`src/middleware.ts` currently adds tracing headers and has its own matcher.
Deployments must ensure that the composed middleware pipeline is invoked for
the page routes that render nonce-protected HTML; otherwise a nonce will not
be generated or propagated for those responses.

## 2. Nonce generation

### 2.1 Entropy and encoding

`generateCryptographicNonce()` allocates a `Uint8Array(16)` and fills it with
`crypto.getRandomValues()`:

```ts
const bytes = new Uint8Array(16);
crypto.getRandomValues(bytes);
return btoa(String.fromCharCode(...bytes));
```

Sixteen independently generated bytes provide 128 bits of entropy:

```text
16 bytes * 8 bits/byte = 128 bits
```

The result is standard Base64 and is inserted into the policy as:

```text
'nonce-<base64-value>'
```

The Base64 value is an encoding of the random bytes; encoding does not reduce
the underlying entropy. A nonce is generated per request and must never be
stored in a cookie, database, cache, or shared server variable.

### 2.2 Fallback requirements

The normal Next.js Edge/Web Crypto runtime provides `crypto.getRandomValues`.
The fallback in `generateCryptographicNonce()` must also preserve the
128-bit-randomness invariant. A fallback that Base64-encodes a UUID string is
not equivalent to encoding 16 freshly generated random bytes and must not be
used as the basis for a strict 128-bit nonce claim. If a runtime lacks
`getRandomValues`, fail closed or use a runtime cryptographic API that returns
16 random bytes.

### 2.3 Lifecycle invariants

For every protected HTML response:

1. The nonce is newly generated for that request.
2. The nonce appears only in request-local headers and the rendered response.
3. The value in the CSP header exactly matches every authorized inline
   script's `nonce` attribute.
4. A nonce from one response is never accepted for another response.

## 3. CSP construction and strict evaluation

`generateCsp(nonce)` emits the policy used by the security headers handler.
The important directives are:

| Directive | Current purpose |
| --- | --- |
| `default-src 'self'` | Denies unspecified origins by default. |
| `script-src 'self' 'nonce-<nonce>' ...` | Allows same-origin scripts and scripts carrying the request nonce. |
| `object-src 'none'` | Disables plugin content. |
| `base-uri 'self'` | Prevents an injected `<base>` from rewriting relative URLs. |
| `frame-ancestors 'self'` | Restricts who may embed the application. |
| `connect-src ...` | Limits fetch, XHR, WebSocket, geocoding, routing, and telemetry destinations. |
| `worker-src 'self' blob:` | Allows same-origin and Blob Web Workers. |
| `img-src 'self' data: blob: https: ...` | Allows application images and configured map/photo providers. |
| `style-src 'self' 'unsafe-inline' ...` | Supports the current styling and map integration. |
| `upgrade-insecure-requests` | Upgrades insecure resource requests in production browsers. |

Strict evaluation must verify all of the following:

- There is exactly one effective CSP policy for the response, or multiple
  policies are intentionally compatible. A second weaker policy does not
  override a stronger policy; browsers enforce all policies.
- Production `script-src` does not contain `'unsafe-inline'`.
- Inline scripts without the exact response nonce are blocked.
- The nonce is unpredictable and different across two fresh responses.
- `script-src` does not contain an unreviewed wildcard or broad third-party
  origin.
- `worker-src`, `connect-src`, `img-src`, and `frame-src` cover only the
  integrations actually used by the page.

`getCSPHeader()` in `src/lib/security/csp.ts` is a legacy helper with
`'unsafe-inline'` and `'unsafe-eval'`. It is not the strict policy and must not
be used for production responses.

## 4. Propagation to React Server Components and hydration

### 4.1 Middleware to Server Components

The security headers handler:

1. Generates the nonce.
2. Builds the CSP string.
3. Sets `x-csp-nonce` on the downstream request headers.
4. Sets `Content-Security-Policy` on the downstream request headers so Next.js
   can discover the nonce while rendering.
5. Sets the same `Content-Security-Policy` on the outgoing response.

`RootLayout` reads `x-csp-nonce` through `headers()` and applies it to the
inline `theme-init` script:

```tsx
const headersList = await headers();
const nonce = headersList.get("x-csp-nonce") ?? "";

<script
  id="theme-init"
  nonce={nonce}
  dangerouslySetInnerHTML={{ __html: THEME_INIT_SCRIPT }}
/>
```

The nonce is request-scoped. It is not a React prop, cookie, URL parameter, or
client storage value.

### 4.2 Next.js-generated scripts and RSC payloads

When Next.js receives the request-scoped CSP header during App Router
rendering, it can attach the discovered nonce to framework-generated inline
bootstrap and hydration scripts. The browser then evaluates those scripts only
when their `nonce` attribute matches the `script-src` nonce.

RSC flight data is not itself executable JavaScript authorization. The
authorization applies to the script/bootstrap element that transports or
hydrates that data. Do not copy the nonce into serialized RSC props or expose
it to client application state.

### 4.3 Client-side navigation

Initial HTML must carry a valid nonce before hydration starts. For a full
navigation, the server creates a new nonce. Client-side route transitions use
Next.js-managed requests and scripts; application code must not manufacture,
persist, or reuse a nonce. Any custom dynamically inserted script must either
be avoided or receive the current server-authorized nonce through a reviewed
server-rendered integration.

## 5. Header verification procedure

Use a production-like response and inspect both request-rendered HTML and
response headers:

```bash
curl -sS -D headers.txt -o page.html http://localhost:3000/venues
```

Check:

```bash
grep -i "content-security-policy" headers.txt
grep -o 'nonce="[^"]*"' page.html
```

The nonce in `page.html` must match the Base64 token in
`'nonce-<token>'` from `headers.txt`. Repeat the request and verify that the
tokens differ. Also verify that an inline script without the nonce is refused
in browser DevTools.

In Chrome or Edge DevTools:

1. Open **Network**, select the document response, and inspect
   `Content-Security-Policy`.
2. Open **Elements** and compare the `nonce` attribute on `theme-init` and
   Next.js bootstrap scripts.
3. Open **Console** and reproduce a blocked resource.
4. Confirm the violation names the expected directive and destination.

Do not treat a successful page load as proof of strict CSP. A page may appear
to work because a legacy policy, a browser extension, or a cached document is
masking a missing nonce.

## 6. Troubleshooting CSP violation reports

### 6.1 Third-party script embeds

Symptoms include a report such as:

```text
Refused to load the script 'https://vendor.example/script.js'
because it violates script-src ...
```

Resolution:

1. Confirm the vendor is required and trusted.
2. Prefer a server-rendered `<Script>` or external script with the current
   nonce over adding `'unsafe-inline'`.
3. Add the exact vendor origin to `script-src` only after review.
4. If the vendor injects inline scripts, require nonce support or isolate it
   in a controlled iframe with a minimal `frame-src` allowlist.
5. Recheck that the vendor does not redirect to an unlisted origin.

Never fix a violation by adding `'unsafe-inline'` to production `script-src`.

### 6.2 Web Workers

Typical report:

```text
Refused to create a worker from 'blob:...' because it violates worker-src.
```

Resolution:

- Same-origin worker files require `worker-src 'self'`.
- Blob-created workers require `worker-src blob:`.
- If a worker imports scripts, validate those imports against the worker's
  execution policy and bundle them locally where possible.
- Do not broaden `script-src` as a workaround for a `worker-src` violation.
- Avoid `data:` workers unless there is a documented, reviewed requirement.

### 6.3 Leaflet map tiles and map integrations

Leaflet tile images are governed by `img-src`, while geocoding, routing, and
map telemetry requests are governed by `connect-src`. A tile failure often
looks like a JavaScript failure but is usually an image or network directive
violation.

For OpenStreetMap, CartoCDN, and Mapbox:

1. Identify the exact failing URL in the console report.
2. Add the origin to `img-src` for raster/vector tile images.
3. Add the origin to `connect-src` for fetch/XHR/WebSocket traffic.
4. Add a script origin only if the page actually loads JavaScript from that
   provider.
5. Keep path and protocol restrictions as narrow as the provider permits.

Do not add `*` to `img-src` or `connect-src` merely to make a tile layer load.

### 6.4 Inline script and hydration failures

Symptoms:

```text
Refused to execute inline script because it violates script-src ...
```

Check, in order:

1. The response has `Content-Security-Policy`.
2. The policy contains the same nonce as the rendered script.
3. `x-csp-nonce` was injected before the Server Component rendered.
4. The page was not served from a cache that reused HTML with an old nonce.
5. No downstream proxy stripped or rewrote the CSP header.
6. The top-level middleware entrypoint actually invokes the security pipeline
   for that route.

### 6.5 CSP report interpretation

Treat `blocked-uri`, `violated-directive`, `effective-directive`, and
`document-uri` as diagnostic data, not authorization input. Do not echo report
values into a CSP header. Group reports by directive and reviewed origin, then
fix the narrowest policy or application issue that explains the report.

## 7. Operational invariants

- Every protected HTML response has a fresh 128-bit nonce.
- No production script policy uses `'unsafe-inline'`.
- Nonces are never logged, persisted, or sent to analytics.
- CSP allowlists are origin-specific and reviewed when dependencies change.
- A CSP change is validated against SSR, RSC hydration, Web Workers, third-party
  embeds, and Leaflet map functionality.
- The response header and rendered nonce attributes are generated from the same
  request-local value.
