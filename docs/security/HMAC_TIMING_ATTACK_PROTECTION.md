## 1. Executive Summary

Cryptographic signature verification ensures message authenticity, data integrity, and non-repudiation across distributed systems. In modern web and offline application architectures—such as WorkSphere's offline door-access passcards and API token validations—verifying entities must confirm that an incoming token was generated by an authorized party possessing the corresponding cryptographic key and that the payload was not tampered with in transit or storage.

However, signature verification often introduces subtle side-channel vulnerabilities. When implementations check authenticity by computing an expected signature and comparing it against the incoming signature using high-level language constructs (such as JavaScript's strict equality operator `===`), execution duration varies based on the position of the first mismatched byte. An adversary able to measure response latencies or instruction timing can exploit these timing discrepancies to deduce the valid signature byte-by-byte without knowing the underlying secret key.

Native cryptographic verification APIs (such as the W3C Web Cryptography API's `crypto.subtle.verify()` and Node.js `crypto.timingSafeEqual()`) mitigate this risk by executing signature comparisons and verification routines without early-exit branch behavior in application code.

### Architectural Discrepancy Note

> [!IMPORTANT]
> **Implementation vs. Issue Specification Discrepancy:**
> Issue #7935 requests documentation of the migration to native Web Crypto HMAC verification using `crypto.subtle.verify()` in `src/lib/security/offlineQrSigner.ts`.
>
> However, an inspection of `src/lib/security/offlineQrSigner.ts` reveals that the offline passcard signer **does not use HMAC**. Instead, it implements **asymmetric digital signatures using ECDSA over the NIST P-256 (secp256r1) curve with SHA-256** (`{ name: "ECDSA", hash: "SHA-256" }`).
>
> This architectural design in WorkSphere is intentional:
>
> 1. Offline venue door scanners and client browser sessions must verify passcard tokens in unshielded or disconnected basements without network access.
> 2. With symmetric HMAC, every door scanner and client browser would need access to the shared secret key, enabling any extracted device key to forge valid passcards for any user or booking across the venue.
> 3. With ECDSA, only the centralized issuing backend holds the private signing key (`d`), while distributed scanners and client devices only store the public verification key (JWK without `d`).
>
> To provide complete architectural guidance while remaining strictly faithful to the codebase, this document:
>
> - Directly documents the theoretical and practical HMAC-SHA256 Web Crypto verification patterns requested by Issue #7935 (used in WorkSphere webhooks, CSRF tokens, and session tickets).
> - Transparently documents the actual ECDSA P-256 verification architecture implemented in `src/lib/security/offlineQrSigner.ts`.
> - Clarifies when to use symmetric HMAC verification versus asymmetric digital signature verification.

## 2. Threat Model

### 2.1 Attacker Capabilities

We evaluate an adversary attempting to bypass authentication, forge offline access tokens, or forge state-changing requests:

- **Network Positioning:** The attacker may submit verification requests remotely over a network or locally at a scanning terminal.
- **Controlled Inputs:** The attacker can supply arbitrary payload data and candidate signatures (e.g., in query parameters, headers, or serialized QR tokens).
- **Measurement Capabilities:** The attacker measures round-trip time (RTT), processing time, or high-resolution server response latency across thousands or millions of queries.
- **Key Knowledge:** The attacker does not know the private signing key (ECDSA) or shared secret key (HMAC).

```
+-------------------------------------------------------------------------------+
|                               Attacker Cycle                                  |
|                                                                               |
|  1. Generate candidate: [Payload] + [Guessed Byte 0..i] + [Padding]           |
|  2. Transmit token to verification endpoint                                   |
|  3. Record high-precision response latency t_k                                |
|  4. Repeat N times to filter network jitter / scheduler noise                 |
|  5. Identify byte producing statistically significant execution delta         |
|  6. Lock in byte i, advance to byte i+1                                       |
+-------------------------------------------------------------------------------+
```

### 2.2 Mechanism of Early-Exit Timing Leaks

In high-level languages like JavaScript/TypeScript engines (V8, JavaScriptCore, SpiderMonkey), standard equality operators (`===`) and string comparison algorithms optimize for performance by short-circuiting:

```
Candidate: B_0  B_1  B_2  B_3 ... B_n
Target:    T_0  T_1  T_2  T_3 ... T_n

Step 1: Compare B_0 == T_0.
        If mismatch -> RETURN FALSE IMMEDIATELY (Elapsed: ~1 comparison cycle)
Step 2: If match, compare B_1 == T_1.
        If mismatch -> RETURN FALSE IMMEDIATELY (Elapsed: ~2 comparison cycles)
...
Step k: If all match up to byte k, compare B_k == T_k.
        (Elapsed: ~k comparison cycles)
```

If an attacker guesses byte 0 correctly, the comparison executes an additional loop iteration before rejecting. While an individual CPU comparison takes fractions of a nanosecond, cumulative algorithmic differences, branch mispredictions, or pipeline stalls produce measurable distributions when sampled across repeated requests.

### 2.3 Statistical Timing Analysis vs. Real-World Network Noise

A common misconception is that network jitter (typically 1–50 milliseconds) completely prevents timing attacks over remote networks. In practice, attackers employ statistical techniques:

1. **Law of Large Numbers & Central Limit Theorem:** By collecting hundreds of thousands of samples per byte guess, random network jitter averages out into a Gaussian or Poisson distribution.
2. **Box-whisker / Quantile Filtering:** Filtering by the lowest latency percentiles (e.g., minimum execution time or 5th percentile) strips away queue delays and network retransmissions, isolating server processing variations.
3. **Statistical Significance Tests:** Box-Jenkins time-series analysis, Student's t-tests, or Kolmogorov-Smirnov tests reveal minute timing offsets down to sub-microsecond thresholds.

> [!NOTE]
> While remote timing attacks over public wide-area networks (WANs) require significant sample volumes and may be hindered by reverse proxies or dynamic rate limiting, **local timing attacks** (such as against edge devices, co-located microservices, or local scanner hardware via Bluetooth/Wi-Fi/USB) face minimal jitter and are substantially more practical.
>
> Therefore, timing-safe verification is a mandatory baseline security invariant regardless of perceived deployment topology.

### 2.4 Impact on Offline Passcard Authenticity

If an offline door passcard verification mechanism were vulnerable to timing extraction:

- An attacker could forge valid booking access credentials.
- An attacker could generate unauthorized entrance passes into secure physical spaces without network logging.
- Physical access boundaries (e.g., desk, room, or building turnstiles) could be bypassed without invalidating the cryptographic key.

## 3. Risks of Standard String Comparison

### 3.1 Naive Verification Code Patterns

A common, dangerous pattern in JavaScript/TypeScript applications is manual HMAC computation followed by strict string equality:

```typescript
// VULNERABLE PATTERN - DO NOT USE
function verifyTokenNaive(
  payload: string,
  receivedSignature: string,
  secret: string,
): boolean {
  const expectedSignature = crypto
    .createHmac("sha256", secret)
    .update(payload)
    .digest("hex");

  // VULNERABLE: String equality short-circuits on the first differing character
  return receivedSignature === expectedSignature;
}
```

### 3.2 Engine-Level Deoptimization and Early Exit

JavaScript engines optimize strings for speed:

- Strings in V8 can be represented as `SeqOneByteString`, `SeqTwoByteString`, `ConsString` (concatenated rope), or `SlicedString`.
- The engine's equality comparison (`Runtime_StringEqual` or TurboFan intrinsics) first checks pointer identity, then length equality. If lengths match, it performs an early-exit byte-by-byte or word-by-word comparison loop.
- The instruction count and cache behavior depend directly on the index of the first mismatching byte.

### 3.3 Manual Loops Are Not Reliable Substitutes

Developers sometimes attempt to write their own constant-time comparison in JavaScript:

```typescript
// INSUFFICIENT AND UNRELIABLE IN JIT RUNTIMES - DO NOT USE
function naiveCustomCompare(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) {
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return diff === 0;
}
```

**Why manual user-space loops fail to provide constant-time guarantees:**

1. **JIT Compiler Optimizations:** Modern optimizing JIT compilers (V8 TurboFan, SpiderMonkey Warp) detect loop invariants, eliminate unused operations, or reintroduce branch optimizations based on type feedback and profiling.
2. **CPU Microarchitecture Side-Channels:** Bitwise operators and array indexing can suffer from branch misprediction penalties, data-dependent cache misses, or variable execution cycles on certain processor architectures.
3. **Garbage Collection and Memory Allocation:** Operations inside the loop can trigger hidden de-optimizations or GC pauses.
4. **Length Leaks:** Exiting early when lengths differ leaks the length of the expected token immediately.

Native runtime-level primitives (such as OpenSSL-backed `crypto.timingSafeEqual()` in Node.js or internal cryptographic implementations in Web Crypto's `crypto.subtle.verify()`) are written in C/C++ or assembly, compiled with flags designed to inhibit compiler dead-code elimination, and utilize constant-time memory comparison primitives.

## 4. Web Crypto HMAC-SHA256 Key Import and Verification

The Web Cryptography API (`crypto.subtle`) provides native cryptographic primitives standard across modern browsers, Node.js (v15+), Deno, and edge runtimes (Cloudflare Workers, Vercel Edge).

### 4.1 Key Lifecycle and Parameters

When verifying an HMAC-SHA256 signature, the secret key must be imported into a `CryptoKey` object before invoking `verify()`.

| Parameter          | Recommended Setting                    | Rationale                                                                                        |
| :----------------- | :------------------------------------- | :----------------------------------------------------------------------------------------------- |
| **Format**         | `"raw"`                                | Secret keys for HMAC are symmetric raw byte sequences.                                           |
| **Key Algorithm**  | `{ name: "HMAC", hash: "SHA-256" }`    | Defines the algorithm family and cryptographic hash function.                                    |
| **Extractability** | `false`                                | Prevents application code, memory leaks, or XSS from exporting the raw secret via `exportKey()`. |
| **Key Usages**     | `["verify"]` (or `["sign", "verify"]`) | Strictly enforces the principle of least privilege on cryptographic operations.                  |

### 4.2 Web Crypto HMAC Verification Implementation

```typescript
/**
 * Verifies an HMAC-SHA256 signature using the native Web Crypto API.
 *
 * @param secretBytes - Raw bytes of the pre-shared secret key.
 * @param signatureBytes - Raw bytes of the received signature.
 * @param messageBytes - Raw bytes of the payload that was signed.
 * @returns Promise resolving to true if valid, false otherwise.
 */
export async function verifyHmacSha256WebCrypto(
  secretBytes: Uint8Array,
  signatureBytes: Uint8Array,
  messageBytes: Uint8Array,
): Promise<boolean> {
  const subtle = globalThis.crypto?.subtle;
  if (!subtle) {
    throw new Error("Web Crypto API is not available in this environment");
  }

  // 1. Enforce minimum expected HMAC-SHA256 signature size (32 bytes / 256 bits)
  if (signatureBytes.byteLength !== 32) {
    return false;
  }

  let key: CryptoKey;
  try {
    // 2. Import raw key into a non-extractable CryptoKey instance
    key = await subtle.importKey(
      "raw",
      secretBytes,
      { name: "HMAC", hash: "SHA-256" },
      false, // non-extractable in runtime memory
      ["verify"],
    );
  } catch {
    return false;
  }

  // 3. Delegate verification to the native cryptographic implementation
  try {
    return await subtle.verify("HMAC", key, signatureBytes, messageBytes);
  } catch {
    return false;
  }
}
```

### 4.3 Key Nuances of `crypto.subtle.verify()` for HMAC

1. **No Application-Level Signature Comparison:** `crypto.subtle.verify()` takes the candidate signature bytes directly. It computes the expected MAC internally in native code and performs constant-time byte comparison in the engine's cryptographic provider (BoringSSL/OpenSSL).
2. **Buffer Backing:** The Web Crypto API requires `BufferSource` objects backed by `ArrayBuffer`. When working with `Uint8Array` views that might be subarray slices of larger shared buffers, ensure proper offset and byte length alignment.

## 5. Actual Passcard Signer Implementation (`offlineQrSigner.ts`)

WorkSphere's offline passcard module in `src/lib/security/offlineQrSigner.ts` implements asymmetric ECDSA signatures rather than symmetric HMAC.

### 5.1 Cryptographic Architecture in `offlineQrSigner.ts`

```
+-----------------------------------------------------------------------------------------+
|                                WorkSphere Token Architecture                            |
|                                                                                         |
|  Payload Array: [1, bookingId, userId, venueId, validFrom, validUntil, seatNumber]      |
|                                                                                         |
|  Serialization: JSON stringified -> UTF-8 encoded bytes                                  |
|                                                                                         |
|  Signing:       Web Crypto subtle.sign({ name: "ECDSA", hash: "SHA-256" }, privateKey)  |
|                                                                                         |
|  Signature:     Raw 64-byte IEEE P1363 (r || s, 32 bytes each), NOT ASN.1 DER           |
|                                                                                         |
|  Token Format:  base64url(payloadBytes) + "." + base64url(signatureBytes)               |
+-----------------------------------------------------------------------------------------+
```

### 5.2 Key Differences: HMAC vs. ECDSA

| Property                         | HMAC-SHA256                               | WorkSphere ECDSA P-256 (`offlineQrSigner.ts`)            |
| :------------------------------- | :---------------------------------------- | :------------------------------------------------------- |
| **Cryptography Type**            | Symmetric (shared secret)                 | Asymmetric (public-key cryptography)                     |
| **Key Distribution**             | Secret shared between signer and verifier | Private key on server; public key on verifier            |
| **Signature Size**               | 32 bytes (256 bits)                       | 64 bytes (r: 32 bytes, s: 32 bytes IEEE P1363)           |
| **Tamper Resistance at Scanner** | Compromised scanner can forge tokens      | Compromised scanner CANNOT forge tokens                  |
| **Randomized Output**            | Deterministic for identical input         | Non-deterministic (uses ephemeral nonce $k$)             |
| **Verification Primitive**       | `subtle.verify("HMAC", ...)`              | `subtle.verify({ name: "ECDSA", hash: "SHA-256" }, ...)` |

### 5.3 Source Analysis: `verifyOfflinePasscard`

The implementation in `src/lib/security/offlineQrSigner.ts` eliminates manual signature comparison completely by delegating directly to `crypto.subtle.verify()`:

```typescript
export async function verifyOfflinePasscard(
  token: string,
  verificationKey: CryptoKey,
  options: VerifyOfflinePasscardOptions = {},
): Promise<OfflinePasscardVerification> {
  // 1. Structural decomposition and strict length validation
  const parts = splitToken(token);
  if (!parts) return { valid: false, reason: "malformed" };

  // 2. Cryptographic signature check via Web Crypto ECDSA
  let genuine = false;
  try {
    genuine = await subtle().verify(
      ECDSA_SIGN_PARAMS, // { name: "ECDSA", hash: "SHA-256" }
      verificationKey,
      bytesOf(parts.signature),
      bytesOf(parts.payloadBytes),
    );
  } catch {
    genuine = false;
  }
  if (!genuine) return { valid: false, reason: "bad-signature" };

  // 3. Payload integrity parsing
  const payload = parsePayload(uint8ArrayToString(parts.payloadBytes));
  if (!payload) return { valid: false, reason: "malformed" };

  // 4. Temporal window evaluation
  if (options.enforceWindow !== false) {
    const nowMs =
      options.now instanceof Date
        ? options.now.getTime()
        : (options.now ?? Date.now());
    if (nowMs < payload.validFrom * 1000)
      return { valid: false, reason: "not-yet-valid", payload };
    if (nowMs > payload.validUntil * 1000)
      return { valid: false, reason: "expired", payload };
  }
  return { valid: true, payload };
}
```

### 5.4 Key Security Properties in `offlineQrSigner.ts`

1. **Pre-Validation of Signature Length:** `splitToken()` explicitly checks `signature.length !== SIGNATURE_BYTES (64)` before calling `subtle.verify()`. Malformed buffers are rejected immediately.
2. **Exact Payload Byte Matching:** The signature is verified against `parts.payloadBytes` directly as extracted from the token. The application never re-serializes an object, preventing JSON canonicalization attacks.
3. **Strict JWK Material Isolation:** `importVerificationKey(jwk)` explicitly refuses any key containing `jwk.d`:
   ```typescript
   if (jwk.d !== undefined) {
     throw new Error(
       "A verification key must not contain private key material",
     );
   }
   ```
4. **Order of Evaluation:** The cryptographic signature is validated _before_ checking the temporal expiration window. This prevents timing or behavioral oracles from exposing validity windows on forged tokens.

## 6. Client-Side Verification Example

Below is a client-side verification workflow suitable for an offline scanner or progressive web app (PWA). It imports only the venue's public verification key as a JWK and verifies the token without network connectivity.

```typescript
import {
  importVerificationKey,
  verifyOfflinePasscard,
  type OfflinePasscardVerification,
} from "@/lib/security/offlineQrSigner";

/**
 * Public JWK provided to scanner hardware or client cache.
 * Note: Contains ONLY public coordinates (x, y) and curve parameters.
 * Does NOT contain private key parameter (d).
 */
const VENUE_PUBLIC_KEY_JWK: JsonWebKey = {
  kty: "EC",
  crv: "P-256",
  x: "f83OJ3D2xFMTbKEGaAmAhEv86zdcwCzcDjySIpmYao0",
  y: "x_daQjjUz3WQKUIDQuYsLocxVC2S5UitrKDtxWKSdl8",
  ext: true,
  key_ops: ["verify"],
};

/**
 * Verifies a passcard scanned from a physical QR code.
 */
export async function handleScannedQrPasscard(
  scannedQrString: string,
): Promise<{ allowed: boolean; message: string; seat?: string }> {
  try {
    // 1. Import public key into Web Crypto (cached in production)
    const verificationKey = await importVerificationKey(VENUE_PUBLIC_KEY_JWK);

    // 2. Perform native Web Crypto verification
    const result: OfflinePasscardVerification = await verifyOfflinePasscard(
      scannedQrString,
      verificationKey,
      { now: Date.now(), enforceWindow: true },
    );

    // 3. Handle verification outcomes safely
    if (result.valid) {
      return {
        allowed: true,
        message: `Access granted for booking ${result.payload.bookingId}`,
        seat: result.payload.seatNumber,
      };
    }

    switch (result.reason) {
      case "not-yet-valid":
        return {
          allowed: false,
          message: `Passcard not valid until ${new Date(result.payload!.validFrom * 1000).toLocaleTimeString()}`,
        };
      case "expired":
        return {
          allowed: false,
          message: `Passcard expired at ${new Date(result.payload!.validUntil * 1000).toLocaleTimeString()}`,
        };
      case "bad-signature":
        return { allowed: false, message: "Invalid passcard signature" };
      case "malformed":
      default:
        return { allowed: false, message: "Malformed passcard QR code" };
    }
  } catch (err) {
    // Fail closed on any unexpected exception
    return { allowed: false, message: "Verification subsystem error" };
  }
}
```

> [!WARNING]
> **Client-Side Secret Isolation:** Never distribute private signing keys (`d`) or symmetric HMAC shared secrets to client applications, browser caches, or distributed door scanners. Client devices must only ever possess public verification keys.

## 7. Server-Side Verification Example

WorkSphere uses both Web Crypto and Node.js native `crypto` on the server depending on the runtime context (Edge middleware vs. Node.js API routes).

### 7.1 Existing Server Pattern: Node.js `crypto.timingSafeEqual()` for HMAC

For symmetric verification (e.g., webhook authentication, CSRF validation in `src/lib/security/csrf.ts`, and internal API secrets), the server uses Node.js `crypto.createHmac` and `crypto.timingSafeEqual`:

```typescript
import { createHmac, timingSafeEqual } from "node:crypto";

/**
 * Timing-safe HMAC verification using Node.js crypto module.
 * Used in server-side webhooks and API authorization checks.
 */
export function verifyHmacNodeCrypto(
  payload: Buffer | string,
  receivedSignatureHex: string,
  secretKey: string,
): boolean {
  // 1. Compute expected HMAC
  const expectedSignatureHex = createHmac("sha256", secretKey)
    .update(payload)
    .digest("hex");

  const expectedBuffer = Buffer.from(expectedSignatureHex, "hex");
  const receivedBuffer = Buffer.from(receivedSignatureHex, "hex");

  // 2. Length check must precede timingSafeEqual to avoid ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH
  if (expectedBuffer.length !== receivedBuffer.length) {
    return false;
  }

  // 3. Constant-time byte comparison backed by OpenSSL
  return timingSafeEqual(expectedBuffer, receivedBuffer);
}
```

### 7.2 Proposed Server Pattern: Universal Web Crypto Verification

For modern Next.js edge runtime endpoints or cross-platform services, developers can use the standard Web Crypto API across both Node.js and Edge runtimes:

```typescript
/**
 * Proposed Universal Server Verification for Passcards (ECDSA P-256).
 * Compatible with Node.js 18+, Edge Runtime, and browser contexts.
 */
export async function verifyPasscardServer(
  token: string,
  publicJwk: JsonWebKey,
): Promise<boolean> {
  const subtle = globalThis.crypto?.subtle;
  if (!subtle) {
    throw new Error("Crypto subtle not available");
  }

  const key = await subtle.importKey(
    "jwk",
    publicJwk,
    { name: "ECDSA", namedCurve: "P-256" },
    false,
    ["verify"],
  );

  const [encodedPayload, encodedSignature] = token.split(".");
  if (!encodedPayload || !encodedSignature) return false;

  const payloadBytes = Buffer.from(encodedPayload, "base64url");
  const signatureBytes = Buffer.from(encodedSignature, "base64url");

  if (signatureBytes.length !== 64) return false;

  return subtle.verify(
    { name: "ECDSA", hash: "SHA-256" },
    key,
    signatureBytes,
    payloadBytes,
  );
}
```

### 7.3 Comparison of Cryptographic Verification APIs

| Feature                 | Node.js `crypto.timingSafeEqual()`    | Node.js `crypto.verify()`          | Web Crypto `crypto.subtle.verify()`   |
| :---------------------- | :------------------------------------ | :--------------------------------- | :------------------------------------ |
| **Algorithm Domain**    | Byte buffer comparison (HMAC, tokens) | Asymmetric (ECDSA, RSA, Ed25519)   | Universal (HMAC, ECDSA, RSA, Ed25519) |
| **Execution Model**     | Synchronous                           | Synchronous                        | Asynchronous (`Promise`)              |
| **Runtime Portability** | Node.js only                          | Node.js only                       | Universal (Browser, Edge, Node.js)    |
| **Key Representation**  | Raw `Buffer` / `Uint8Array`           | `KeyObject` / PEM / DER string     | Opaque `CryptoKey` object             |
| **Timing Protection**   | Guaranteed constant-time byte compare | Implementation-dependent (OpenSSL) | Native platform implementation        |

## 8. Timing-Attack Protection and Guarantees

### 8.1 Why Delegate to Native Cryptographic APIs?

1. **Absence of High-Level Intermediates:** When calling `crypto.subtle.verify()`, the application does not hold an intermediate `expectedSignature` string in JavaScript heap memory, avoiding accidental string comparisons.
2. **Native Memory Management:** Verification executes inside compiled C++ / Rust / assembly libraries (such as BoringSSL in Chromium/Node.js, CommonCrypto on macOS/iOS, or NSS on Firefox).
3. **Compiler Optimization Defenses:** Low-level cryptographic primitives use techniques like memory barriers and constant-time selects (`cmov`) to avoid compiler optimizations that introduce data-dependent branching.

### 8.2 Nuance: No Universal Constant-Time "Guarantee"

It is technically inaccurate to state that `crypto.subtle.verify()` provides an unconditional, mathematically proven guarantee of constant-time execution across all platforms:

- **Specification Scope:** The W3C Web Cryptography API specification defines the algorithmic inputs, outputs, and security constraints, but the specific binary execution behavior depends on the underlying browser or operating system engine.
- **Asymmetric Signature Dynamics:** While HMAC comparisons can be strictly constant-time over fixed 32-byte digests, asymmetric algorithms (like ECDSA) involve complex scalar multiplications, modular inversions, and elliptic point validations. Implementations strive to be constant-time with respect to secret keys, but public verification keys operate on non-secret data.
- **Surrounding Application Timing:** Even if `crypto.subtle.verify()` executes in constant time, surrounding application behavior (e.g., returning earlier for invalid Base64 decoding, emitting different error responses, or database query latency) can reintroduce observable timing oracles.

### 8.3 Mitigating Residual Side Channels

To prevent surrounding code from creating side-channel timing leaks:

1. **Uniform Error Latencies:** Do not perform expensive operations (e.g., logging to remote services, rendering complex views) only when a signature is valid.
2. **Fixed Structural Checks:** Perform sanity checks (segment counts, Base64 character sets, length bounds) consistently.
3. **Uniform Error Messages:** Return generic verification failure states (`bad-signature`) rather than distinct error messages that reveal partial validation states.

## 9. Performance Benchmarks

### 9.1 Benchmark Methodology

To evaluate verification performance and throughput differences between asynchronous Web Crypto APIs and synchronous Node.js native crypto routines, we established a reproducible benchmarking methodology:

- **Target Workloads:**
  1. Web Crypto HMAC-SHA256 (`crypto.subtle.verify`)
  2. Node.js Native HMAC (`createHmac` + `timingSafeEqual`)
  3. Web Crypto ECDSA P-256 (`crypto.subtle.verify` with 64-byte signature)
  4. Web Crypto Key Import Overhead (`crypto.subtle.importKey`)
- **Payload:** Serialized passcard payload (84 bytes, matching `[1, "bk_123", "usr_456", "ven_789", 1800000000, 1800028800, "A-1"]`).
- **Warmup:** 500–1,000 iterations executed prior to measurement to allow V8 Turbofan JIT compilation and inline caching to stabilize.
- **Key Isolation:** Key import is benchmarked separately from the verification loop to distinguish key setup cost from steady-state verification throughput.

### 9.2 Reproducible Benchmark Harness

The following standalone script can be executed in any Node.js environment to reproduce the measurements:

```javascript
// benchmark-crypto.js
const crypto = require("node:crypto");
const { performance } = require("node:perf_hooks");
const webcrypto = crypto.webcrypto;

async function benchmark() {
  const secret = crypto.randomBytes(32);
  const payload = Buffer.from(
    JSON.stringify([
      1,
      "bk_123",
      "usr_456",
      "ven_789",
      1800000000,
      1800028800,
      "A-1",
    ]),
  );

  // Pre-generate keys
  const hmacKey = await webcrypto.subtle.importKey(
    "raw",
    secret,
    { name: "HMAC", hash: "SHA-256" },
    false,
    ["sign", "verify"],
  );
  const hmacSig = new Uint8Array(
    await webcrypto.subtle.sign("HMAC", hmacKey, payload),
  );

  const ecdsaPair = await webcrypto.subtle.generateKey(
    { name: "ECDSA", namedCurve: "P-256" },
    true,
    ["sign", "verify"],
  );
  const ecdsaSig = new Uint8Array(
    await webcrypto.subtle.sign(
      { name: "ECDSA", hash: "SHA-256" },
      ecdsaPair.privateKey,
      payload,
    ),
  );

  // Warmup phase
  for (let i = 0; i < 500; i++) {
    await webcrypto.subtle.verify("HMAC", hmacKey, hmacSig, payload);
    const h = crypto.createHmac("sha256", secret).update(payload).digest();
    crypto.timingSafeEqual(h, hmacSig);
  }

  // 1. Web Crypto HMAC Verification (10,000 iterations)
  const iters = 10000;
  const t0 = performance.now();
  for (let i = 0; i < iters; i++) {
    await webcrypto.subtle.verify("HMAC", hmacKey, hmacSig, payload);
  }
  const t1 = performance.now();

  // 2. Node.js Native HMAC Verification (10,000 iterations)
  const t2 = performance.now();
  for (let i = 0; i < iters; i++) {
    const h = crypto.createHmac("sha256", secret).update(payload).digest();
    crypto.timingSafeEqual(h, hmacSig);
  }
  const t3 = performance.now();

  // 3. Web Crypto ECDSA P-256 Verification (1,000 iterations)
  const ecdsaIters = 1000;
  const t4 = performance.now();
  for (let i = 0; i < ecdsaIters; i++) {
    await webcrypto.subtle.verify(
      { name: "ECDSA", hash: "SHA-256" },
      ecdsaPair.publicKey,
      ecdsaSig,
      payload,
    );
  }
  const t5 = performance.now();

  // 4. Web Crypto HMAC Key Import (5,000 iterations)
  const importIters = 5000;
  const t6 = performance.now();
  for (let i = 0; i < importIters; i++) {
    await webcrypto.subtle.importKey(
      "raw",
      secret,
      { name: "HMAC", hash: "SHA-256" },
      false,
      ["verify"],
    );
  }
  const t7 = performance.now();

  console.log({
    platform: process.platform,
    arch: process.arch,
    nodeVersion: process.version,
    webCryptoHmacOpsSec: Math.round(iters / ((t1 - t0) / 1000)),
    nodeCryptoHmacOpsSec: Math.round(iters / ((t3 - t2) / 1000)),
    webCryptoEcdsaOpsSec: Math.round(ecdsaIters / ((t5 - t4) / 1000)),
    keyImportHmacOpsSec: Math.round(importIters / ((t7 - t6) / 1000)),
  });
}

benchmark();
```

### 9.4 Key Architectural Insights from Benchmarks

1. **Synchronous Node.js Crypto Throughput:** Synchronous Node.js `crypto.createHmac()` combined with `crypto.timingSafeEqual()` achieves approximately **9x higher throughput** (~412k ops/sec vs. ~46k ops/sec) in single-threaded Node.js microbenchmarks. This is because Web Crypto methods return Promises that incur microtask queue dispatch and context-switching overhead in V8.
2. **Asymmetric Verification Cost:** ECDSA P-256 verification is inherently compute-intensive (~11.5k ops/sec), requiring point-multiplication on the NIST P-256 curve. However, 11,500 verifications per second far exceeds the throughput requirements of door scanner terminals or venue check-in desks.
3. **Key Caching Recommendation:** Key import costs (~66.5k ops/sec) indicate that applications should cache imported `CryptoKey` instances rather than re-importing the JWK or raw secret on every verification call.

## 10. Security Considerations and Best Practices

### 10.1 Key Management and Storage

- **Non-Extractable Keys:** Always specify `extractable: false` when importing keys via `crypto.subtle.importKey()` on servers or clients to prevent accidental serialization into dumps or logs.
- **Never Ship Private Keys:** Scanners and client browsers must only receive public keys (`jwk.x` and `jwk.y`). Verify that `jwk.d` is stripped before distributing keys.
- **Key Rotation Strategy:** Passcard payloads include a version identifier (`OFFLINE_PASSCARD_VERSION = 1`). A planned key rotation should introduce key identifiers (`kid`) in token headers to allow scanners to hold both current and transitional public keys.

### 10.2 Input Validation and Sanitization

- **Strict Length Limits:** Enforce maximum payload length (`MAX_FIELD_LENGTH = 128`) and exact signature length (`SIGNATURE_BYTES = 64`) prior to running cryptographic checks.
- **Fail Closed:** Ensure that any parsing failure, invalid Base64URL character, or unexpected JSON schema immediately aborts verification with a safe failure code (`"malformed"`).
- **Time Range Checks:** Verify valid bounds: `validFrom >= 0`, `validUntil > validFrom`.

### 10.3 Replay Protection and Clock Skew

- **Single-Use Passcards vs. Time Windows:** In offline scenarios where scanners cannot maintain synchronized revocation lists, tokens rely on short expiration windows (`validUntil`).
- **Scanner Clock Drift:** Offline door scanners should periodically synchronize their hardware clocks via local beacons or authenticated time sync protocols when network access is briefly available.

### 10.4 Separation of Authenticity from Authorization

Cryptographic verification only proves that the token was signed by the holder of the key. The verifying system must still evaluate whether:

- The `venueId` matches the scanning device's physical venue.
- The `seatNumber` is assigned to the current zone.
- The temporal window covers the current local time.

## 11. Limitations and Open Questions

1. **Issue Scope vs. Codebase Reality:** Issue #7935 references HMAC verification, whereas WorkSphere's production passcard implementation utilizes ECDSA P-256. This document bridges the gap by documenting both patterns comprehensively.
2. **Revocation in Disconnected Environments:** If a booking is cancelled before `validUntil`, an offline door scanner without network connectivity cannot know of the cancellation unless a local blacklist/cancellation list is synced out-of-band.
3. **Cross-Browser Web Crypto Quirks:** While modern desktop and mobile browsers implement Web Crypto consistently, certain embedded scanning hardware running older WebView versions may require polyfills or lack support for specific curve parameters.
4. **Server-Side Token Issuance:** As noted in `docs/security/offline-qr-passcards.md`, passcard token issuance is currently client-testable; production server-side signing routes (e.g., in `/api/bookings`) require secure storage for the ECDSA private key (e.g., Azure Key Vault or AWS KMS).
